有希望的方向

H1暫定假說

保留薄 skill，可能比新增獨立 runner 更符合日常專案探索。

依據: 暫定假說；依據 SKILL.md／HARNESS.md 以 host 為唯一 Organizer 的設計，以及 .claude／.agents 兩個 wrapper 都只轉指向同一份 SKILL.md。尚未測試跨 host 接手成本。

下一個檢查: 用同一份研究資料測試另一個 host 能否找到下一步。

H2暫定假說

探索與決策分流之後，最值得做的下一步是「接手」：讓下一個 host 只讀 state.json 就能延續探索，不需要跨專案資料庫。

依據: 暫定；hypotheses、planned_checks、open_questions 三個容器在基準版本已存在且可 patch，但四個 field packages 裡全是空的，先前沒有任何 gate 或 render 使用它們。

下一個檢查: 讓第二個 host 在不看 report.html 的情況下只讀 state.json，指出下一個檢查，比對是否與 planned_checks 一致。

H3暫定假說

先前發現的免費 route 缺口，對探索廣度的影響可能大於再加一個付費 provider。

依據: 暫定；規格已將此缺口另行追蹤，本輪未驗證，也未讀取任何 route 的實際使用資料。

下一個檢查: 盤點四個 field packages 的 events.jsonl，統計 free route 與 paid route 的實際使用比例。

已排除的方向

H4已排除

同一 session 內從 explore 自動升格為 decision 合約。

依據: 暫定判斷；來自規格第 79 行的範圍說明。

排除原因: 規格明確將同 session 合約切換與自動升格排除在本輪之外；而且若探索與決策共用同一個 status 生命週期，「本輪在找方向還是做決策」會再度變得不可分辨。

H5已排除

以分支數或文件數作為探索品質分數。

依據: 暫定判斷；來自規格第 111 行的人工評估說明。

排除原因: 規格反對以篇數或分支數評分；這類指標會把探索變回填表，與本輪「降低操作負擔」的目的相反。

本輪仍不知道的事

  • 另一個 host 接手探索結果的成本要怎麼量測？目前沒有基準，也沒有失敗案例。
  • 先前發現的 HTML report hash 缺口是否影響探索型報告的可信度？本輪未處理。
  • 探索途中若真的驗到一條正式主張，應留在同一 package 記錄為 claim，還是另開 decision 合約？本輪只允許前者的記錄，不產生 verdict。

最值得做的下一個檢查

  • P1 用同一份 state.json 讓第二個 host（未讀報告）指出下一步，比對其答案與 planned_checks 是否一致。 （針對 H1, H2）
  • P2 盤點四個 field packages 的 free／paid route 使用比例，判斷 H3 是否值得深入。 （針對 H3）
